# Agawa-HP UX 优化执行方案

日期：2026-11-03
状态：待阿川审核的执行方案
范围：全站导航、页面布局、项目与文章的发现路径，以及鱼的长文和札记的组织方式。

这次优化以“访客容易找到想看的内容”为目标。项目与博客作为两个核心入口，在首页第一屏同时出现；首页后续先展示项目，再展示技术文章。博客承担统一阅读入口，鱼的长文和札记集中到同一内容空间，通过清楚的入口和页面内导航互相连接。

本方案整理自 bmad-ux 与 bmad-party-mode 讨论。以下区分用户已明确的需求与讨论形成的推荐设计；推荐设计由阿川做最终审核。本次交付为方案，未实施网站改版。

## 1. 需求与设计取舍

### 已明确的需求

- 第一类访客是合作方，主要通过项目和技术博客了解阿川。
- 第二类访客是朋友，主要寻找博客。
- 优先优化导航，让访客发现内容、到达目标，无须寻找不起眼的按钮。
- 重新规划各页面布局；网站继续服务中文、英文和日文读者。
- 由多角色讨论提出方案，阿川最终审核。

### 推荐采用的设计

| 设计事项 | 推荐决定 | 理由 |
| --- | --- | --- |
| 首页重心 | 项目与博客入口并重，内容展示顺序为项目在前、技术文章紧随 | 同时服务两类主要访客，并优先呈现合作方关注的内容 |
| 全站导航 | 首页、项目、博客、关于我、联系；语言切换独立呈现 | 减少理解成本，把主要目的地前移 |
| 手机导航 | 项目、博客直接可见，其余入口放入带文字的菜单 | 保留主要去向，避免入口全部藏进图标 |
| 博客组织 | 默认展示全部公开文章，支持少量主题筛选，显示可靠的作者信息 | 访客可直接阅读，也能缩小范围 |
| 鱼的内容 | 在博客下集中为“鱼的文字”，内部提供长文与札记 | 把同一署名下的两种表达放在一起 |
| 首页展示鱼的札记 | 第一阶段暂不加入，作为后续选项 | 讨论尚有分歧，先确保项目与技术文章的主要路径清楚 |
| 搜索与复杂分类 | 第一阶段不增加 | 当前内容规模较小，先改善现有入口与列表 |

“鱼的文字”为推荐入口名，附说明“长文与日常札记”。长文栏目保留“鱼的博客”，短内容保留“鱼的札记”。鱼的身份介绍、文章作者归属不能从署名或收录位置自行推断。

## 2. 当前结构与需要解决的问题

以下是本地源码基线，尚未经过本轮浏览器与真实访客验证。

| 当前结构 | 优化动作 |
| --- | --- |
| 首页展示区最小高度接近一屏，目录与精选作品位于其后 | 压缩展示区，让介绍和两个主要入口同时出现 |
| 主导航字号为 11px；手机端导航为非固定定位 | 提高文字和点击区域的可辨认性，保留滚动中的主要去向 |
| 博客页先显示不可点击的“写作方向”，再显示文章列表 | 将文章前移，主题转为真正可用的筛选控件 |
| 鱼的博客入口是一行链接，札记入口在首页目录 | 博客页增加醒目的内容空间入口，鱼的两个栏目互相可达 |
| 《把「人」演得很像》同时被总博客列表和鱼的博客收录 | 继续链接到同一文章，核对并显示作者，避免重复建文 |
| 项目以完整介绍依次展开 | 增加页首项目索引，提高具体项目与外部应用的可达性 |

当前三语数据均包含 3 个项目、5 篇总博客索引文章、1 篇鱼的长文和 3 条札记。总博客与鱼的长文存在重复收录，这些数量不能相加作为独立文章总数。

## 3. 信息架构与路径

```text
首页
├─ 项目 → 项目快捷索引 → 具体项目介绍 → 打开应用或访问网站
├─ 博客 → 全部文章／主题筛选 → 文章 → 继续阅读
│        └─ 鱼的文字 → 长文 ⇄ 札记
├─ 关于我 → 项目／博客／联系
└─ 联系 → 联系方式／相关项目
```

第一阶段沿用现有地址：项目页为 `works.html`，博客为 `blog.html`，鱼的长文入口为 `fish-blog.html`，札记为 `notes.html`。将 `fish-blog.html` 扩充为鱼的内容空间入口，不额外增加只负责中转的页面。

鱼的两页共享“长文／札记”栏目导航。`fish-blog.html` 默认展示长文，`notes.html` 展示札记；切换栏目进入相应地址，清楚标记当前栏目。推荐位置提示为“博客 › 鱼的文字 › 长文／札记”，前两级分别返回博客与鱼的空间入口。

### 路径验收情景

以下人物为走查用的假设访客，不是真实用户研究结果。

| 情景 | 访问过程 | 成功节点 |
| --- | --- | --- |
| 合作方陈女士想体验班车应用 | 首页 → 项目 → JAIST Shuttle Next → 打开应用 | 找到实际应用，而非只读到介绍 |
| 合作方陈女士想了解技术思考 | 首页技术文章或博客 → 技术筛选 → 文章 | 找到技术文章并看清内容与作者 |
| 朋友小林想读最近更新 | 首页 → 博客 → 最新公开文章 | 无须先经过介绍或选择作者才能阅读 |
| 小林想继续看鱼的短观察 | 博客 → 鱼的文字 → 札记 | 能读到短内容，也知道如何切回长文和博客 |
| 直接打开文章的访客想看项目 | 文章 → 全站项目入口 | 不需要先回首页寻找入口 |

从任一公开内容页到项目列表或博客列表，目标为一次导航操作；窄屏下这两个入口仍直接可见。从博客进入鱼的空间为一次操作，长文与札记之间切换为一次操作。路径步数是结构验收目标，不代表已验证的易用性效果。

## 4. 页面调整

### 4.1 全站导航

- 桌面导航按“首页、项目、博客、关于我、联系”排列，文案随当前语言切换。
- 品牌链接明确返回首页；当前栏目同时通过文字样式和 `aria-current` 标记。
- 手机端保留品牌、项目、博客和文字“菜单”。菜单包含首页、关于我、联系和语言选项，具体排列通过窄屏原型确定。
- 导航采用紧凑的顶部固定或粘性布局。长文章滚动时仍可到达项目与博客，且不遮挡正文、锚点标题和键盘焦点。
- 菜单支持点击展开和收起、Escape 关闭、关闭后焦点回到触发按钮；离开菜单区域不会遇到不可见的可聚焦项。
- 语言入口显示当前语言，展开后明确提供中文、English、日本語。切换时保持当前页面或对应文章，不送回首页。
- 页脚增加清楚的主要页面链接，作为阅读结束后的第二组去向。

### 4.2 首页

从上到下调整为：

1. 简短介绍与个人视觉，并列显示“查看项目”“阅读博客”。
2. 精选项目：沿用现有三个项目，展示图片、项目名、用途摘要和明确链接。
3. 技术文章：最多展示两篇经核对的公开文章，提供“查看全部博客”。
4. 其他近期文章：最多两篇，与技术区去重；没有合适内容时不显示空壳区域。
5. 简短个人介绍与关于、联系入口。
6. 页脚导航。

现有个人文字和视觉元素根据新布局调整位置，保留个人表达。原来占据主要篇幅的目录不再作为核心导航；去向由顶部导航和各区块入口承担。

第一屏验收以入口可见为目标，不要求在所有设备上同时塞入项目卡片。手机端将两个入口放在大幅图片之前，避免先滚过图片才能选择。

### 4.3 项目页

- 标题和简短说明之后直接显示三个项目的快捷索引，点击定位到对应介绍。
- 每个项目依次呈现：名称与用途、截图、摘要、已有项目说明、明确的外部访问入口。
- 将泛化的“查看项目”按目标改为“打开应用”或“访问网站”，使访客能预测点击结果。
- 仅在资料可核实时补充“我的贡献”和项目状态，不根据技术栈或图片推断工作量、成果和上线情况。
- 保留 `works.html#项目ID` 深链接；锚点定位后标题不被导航遮挡。
- 有真实关联文章时展示“相关技术文章”，没有关联时省略。

### 4.4 博客页

- 页首简短说明之后直接进入阅读区域，不再先铺陈不可操作的写作方向。
- 在首批文章附近提供完整可点击的“鱼的文字”入口，带“长文与日常札记”说明；不设置必须先选择才能看到文章的中间页。
- 默认显示全部公开文章，按日期倒序。初步主题为“全部、技术实践、其他主题”，最终名称和归类须核对现有文章。
- “技术实践”为明确的文章属性，不依靠标题关键词自动猜测；混合主题文章可拥有多个主题，列表中只显示一次。
- 文章条目展示标题、简短摘要、日期、主题和经确认的作者信息。整条可点击，保留清楚的文字链接语义。
- 主题筛选写入 URL 参数；刷新、浏览器返回和从文章返回时能恢复筛选。直接访问列表时默认全部。
- 无匹配结果时显示说明和“查看全部文章”操作，不留下空白区域。

### 4.5 鱼的文字

- `fish-blog.html` 与 `notes.html` 使用同一空间名称、简短说明和栏目导航，分别明确当前为“鱼的博客”或“鱼的札记”。
- 长文列表使用与总博客一致的文章卡片与链接规则；同一篇文章维护同一组既有三语 URL。
- 札记直接展示日期、内容和来源标题；外部视频链接使用可理解的来源文字，不只显示 BV 编号。
- 两个栏目均提供“返回全部博客”，页末可切换到另一栏目。
- 暂不增加独立札记详情页、日历归档或复杂分页；内容增长后再评估。
- 不擅自为鱼添加身份说明。作者与署名核对完成前，沿用现有已公开的名称。

### 4.6 文章页

- 保留独立语言文章地址，在顶部提供当前位置和返回博客入口。
- 长文章依据现有标题生成可跳转目录。建议以五个及以上正文二级标题作为初始规则，排除资料说明等非正文部分，并在原型中确认。
- 桌面可采用侧边目录，手机采用带“本文目录”文字的折叠区；标题锚点可被键盘访问并正确定位。
- 文末提供返回博客、最多两篇相关公开文章，以及有真实关联时的项目入口；无相关内容时仅显示返回入口。
- 总博客和鱼的空间收录同文时，作者信息保持一致。第一阶段统一以博客作为文章返回目的地，不根据来源猜测作者或创建文章副本。
- 保留文章自身的标题、描述、语言属性和 SEO 信息。

### 4.7 关于与联系

- 关于页在简短介绍后提供项目、技术文章和联系入口，详细经历放在后面。
- 联系页先显示实际可用的联系方式，再显示其他渠道；保留清楚的项目与博客去向。
- 两页沿用同一导航、语言切换和页脚规则。

## 5. 数据与实现边界

沿用静态 HTML、CSS、JavaScript 和 JSON，不引入新框架。主要调整位置如下：

| 文件 | 计划变更 |
| --- | --- |
| 根目录普通页面 HTML | 导航顺序、页面区块顺序、菜单和栏目结构 |
| 全部现有文章语言文件 | 统一导航、目录、返回与继续阅读区域 |
| `assets/css/styles.css` | 导航可读性、入口层级、页面网格、响应式和交互状态 |
| `assets/js/main.js` | 菜单、筛选与恢复、首页文章展示、目录及鱼的栏目交互 |
| `assets/data/site.{lang}.json` | 三语界面文案、文章属性、作者显示与真实内容关联 |

开始编码前先保存并核对当前工作区差异。三份语言 JSON 已有未提交修改，实施必须在这些修改之上增量完成，不回退、不批量重写无关内容。

数据准备建议为总博客条目增加稳定的文章 ID，以及经核对的主题和作者 ID；关联文章和项目使用稳定 ID。三语共用同一 ID，展示名称分别本地化。首页、总列表、作者空间和推荐区域据此去重。字段命名在实施时结合现有结构确定。

公开展示区统一应用现有可见性规则。首页精选、主题筛选、作者空间入口摘要和继续阅读推荐均不得额外暴露未解锁私密文章的信息；保持既有私密内容处理约定。

三语新增界面文案集中维护在现有 JSON 中，普通页面不复制三套 HTML。文章仍使用各自语言文件和 `data-article-lang`、`data-lang-target`；修改共享导航时必须覆盖所有文章语言版本。

现有 URL、项目 ID、canonical 与语言对应关系优先保留。缓存版本随资源更新统一处理，避免新 HTML 配上旧脚本或旧 JSON。文档和原型放在开发目录，不进入 Pages 公开产物。

## 6. 实施顺序与交付物

| 阶段 | 工作 | 交付与完成条件 |
| --- | --- | --- |
| A 内容核对 | 保存现有差异；列出全部页面；核对作者、主题、项目与文章关联 | 页面清单和内容映射表；不确定字段单独列出，不靠猜测补齐 |
| B 原型 | 为首页、博客、鱼的空间、项目与长文制作桌面和手机原型；包括菜单展开态 | 可通过本地 HTTP 浏览的原型，附其余页面的布局说明；由阿川审核结构与入口 |
| C 共用导航 | 实施全站导航、手机菜单、语言入口、页脚和焦点状态 | 全部页面三语入口一致，直达链接与菜单可用 |
| D 主要页面 | 实施首页、项目、博客和鱼的两栏目 | 两类主要访客路径完整，筛选与栏目切换可恢复 |
| E 阅读与辅助页 | 文章目录、继续阅读、关于和联系页入口 | 长文直达访客也能清楚前往项目或博客 |
| F 验证与审核 | 三语、链接、窄屏、键盘和内容可见性检查；完整路径走查 | 提交本地预览、检查记录、截图及未解决项，由阿川最终审核 |

先审核可操作原型，再推进批量文章页面修改，减少布局方向变化带来的返工。实施中的常规细节由执行者处理；改变本方案核心入口或内容归属时，明确列出差异供审核。

本计划不含提交、推送或正式发布。现有工作流在推送 `main` 后会触发 Pages 部署，因此发布应作为审核通过后的独立动作。

## 7. 验收标准

### 导航与发现

- 首页初次加载时，“查看项目”“阅读博客”在桌面和手机首屏均可见，包含英语和日语较长文案。
- 所有页面都有一致的项目、博客入口；手机端不用展开菜单就能看到这两个去向。
- 博客开头可发现鱼的空间入口；鱼的长文和札记各一次操作互相切换。
- 每个导航链接、卡片和按钮都有可预测的文字；不以颜色、悬停效果或单独箭头承担唯一提示。
- 阅读到文章末尾时能返回列表或继续阅读，无须滚回页首。

### 布局与交互

- 在 360、390、768、1280 和 1440 CSS 像素宽度检查；同时检查约 320 CSS 像素的窄视口重排和文本放大。
- 页面整体无横向溢出；需要横向阅读的表格在独立容器内滚动。
- 主导航、菜单和主要入口目标尺寸建议至少 44 × 44 CSS 像素，留出间距，并提供可见焦点。
- 仅用键盘可完成导航、菜单开关、筛选、目录跳转和语言切换；无焦点丢失或陷阱。
- 固定导航不覆盖锚点标题与聚焦元素；页面提供跳到正文入口，减少重复经过全站导航。
- 普通文字与背景的对比度目标至少 4.5:1，大字至少 3:1；当前栏目和选中状态不只依赖颜色。
- 关闭或减少动画的系统偏好得到尊重，内容不依赖入场动画才可见。
- 语言数据加载失败时保留可用导航，并显示简短错误和重试操作；无文章和无筛选结果有明确状态。

### 内容、语言与链接

- 中英日逐页检查导航、栏目、卡片、空状态及语言切换，语言改变后仍在对应内容中。
- 作者、主题和首页精选有明确内容依据；鱼的身份及项目贡献不自行编写。
- 同文跨栏目收录不生成重复文章，不重复出现在同一个推荐列表。
- 私密文章未解锁时不进入新增公开发现区域。
- 旧文章 URL、项目锚点、外部应用入口、canonical 和原有语言对应关系仍有效。
- 执行 JavaScript 语法检查、三份 JSON 解析、差异空白检查和新增／修改链接检查；浏览器检查控制台及资源加载。
- 所有预览通过本地 HTTP 服务器进行，不使用 `file://`。

### 访客走查与证据

按第 3 节情景逐项走查，记录实际到达路径、错误入口与需要提示的位置。条件允许时邀请一位接近合作方、一位接近朋友情景的人，各自完成找项目、找文章和找札记任务；不提前告诉他们入口位置。

真实走查是否开展、参与人数与发现分别记录。源码检查、浏览器验证和真实访客反馈应分开报告；没有真实走查时，不宣称找寻时间或任务成功率已改善。

## 8. 本轮审核重点

阿川审核本方案时，优先看以下五项，而非提前确定配色或装饰：

1. 首页是否采用“两个主入口并重，项目先展示、技术文章紧随”的结构。
2. 手机端是否直接保留项目与博客，把其他入口收进文字菜单。
3. 是否以“鱼的文字”集中长文和札记，并继续放在博客体系内。
4. 第一阶段是否暂不在首页展示鱼的最新札记。
5. 先核对内容与制作原型，再批量实施的顺序是否符合预期。

以上为本轮推荐取舍，未标记为用户已批准。颜色、字体、图像比例及详细间距在原型阶段确定；后续如形成完整视觉与体验规范，再分别整理为 `DESIGN.md` 和 `EXPERIENCE.md`，本方案不替代这两份规范。
